# Модель дохода: ритм планирования отдельно от источников денег

Спека к [issue #26](https://github.com/GarroV/multa/issues/26). Поглощает [#27](https://github.com/GarroV/multa/issues/27) (пресеты выплат с зашитыми датами) и закрывает его. Написана после фидбека основателя по скриншоту шага 2 онбординга (2026-07-29).

Статус: дизайн зафиксирован, план имплементации — отдельным документом.

## Задача

Онбординг спрашивает один ритм выплат и **одно** число «примерно сколько каждая выплата». Отсюда три дефекта, и все три — про то, что одна сущность делает две несовместимые работы:

1. Выплаты не одинаковые: аванс и зарплата различаются днём и суммой, и задаются обычно процентами от оклада.
2. Источник не один: основная работа плюс недельная подработка плюс разовый гонорар плюс «когда как».
3. «10-е и 25-е» и «каждые две недели» в интерфейсе читаются как одно и то же — пользователь выбирает ярлык, не видя последствий.

Сегодня ожидаемый доход берётся из скалярной колонки воркспейса ([assemble.ts:306](../../../apps/api/src/plan/assemble.ts#L306)), поэтому план периода 10–25 и план периода 25–10 численно одинаковы, хотя приходят разные деньги.

## Ключевое разделение

Две независимые вещи, которые сейчас слиты в один `PeriodConfig` + одно число:

**Ритм планирования** — настройка воркспейса. Отвечает на вопрос «за какой отрезок я планирую»: два раза в месяц (дни задаёт пользователь), раз в месяц N-го, цикл в N недель от реальной даты выплаты. Это существующая колонка `workspaces.period_anchors` (хранит `PeriodConfig` из `@multa/core`) плюс новое правило выходных. `generatePeriods` остаётся источником правды о границах.

**Источники дохода** — плоский список, только про деньги: метка, расписание, сумма или процент от оклада, валюта, стабильность, период жизни. Ни одного служебного поля про границы периодов. Ожидаемый доход периода = сумма событий всех активных источников внутри `[startsOn, endsOn)`.

Почему не «якорный источник задаёт ритм»: пометка «этот источник задаёт границы периодов» — техническая деталь планировщика, протёкшая в предметную сущность «зарплата». Хуже того, при плоском списке источников она не работает: аванс и зарплата — два источника по одному дню каждый, якорём может быть только один, и полумесячный ритм 10→25→10 (эталон планирования основателя — «Кетчуп в Химках») деградирует до месячного 10→10, где 10-го числа в «цифру дня» попадают деньги, которые придут только 25-го.

Почему недельная подработка не двигает границы: если бы каждый приход открывал период, месяц нарезался бы на 2–3-дневные отрезки, и каскад (долги → корзины → конверты → категории) вместе с «цифрой дня» стал бы бессмыслицей — планировать на три дня нечего. При разделении подработка добавляет 4–5 приходов **внутрь** периода.

### Отклонения от текста #26

Текст issue описывал якорный источник; здесь это заменено. Расхождения, чтобы issue и спека не противоречили друг другу:

| В #26 | Здесь | Почему |
|---|---|---|
| `isAnchor: boolean` на источнике, ровно один | нет такого поля; ритм — настройка воркспейса | Пометка «задаёт границы периодов» — деталь планировщика в предметной сущности «зарплата». При плоском списке источников она к тому же ломает полумесячный ритм (см. выше). |
| `weekendRule` на источнике | `workspaces.payday_weekend_rule`, одно на воркспейс | Границы периода зависят от ритма; правило платёжного календаря — конвенция страны, не свойство работы. |
| Инвариант «сумма процентов = 100%» | подсказка в форме, не блокировка | В плоском списке нет группы, по которой суммировать. |
| `weekly`, `monthly-nth-weekday` в модели | выкинуты | `weekly` = `every-weeks{weeks:1}`; nth-weekday — YAGNI. |
| `workspaces.period_anchors` удалить | остаётся (это ритм) | Ритм больше не выводится из источников, значит колонка нужна; удаляется только скалярный `expected_income_minor`. |

## Модель ядра (`packages/core/src/income.ts`)

```ts
export type WeekendRule = 'as-is' | 'before' | 'after';

export type IncomeSchedule =
  | { kind: 'monthly-days'; days: number[] }              // 10 и 25 (одинаковыми суммами)
  | { kind: 'every-weeks'; weeks: number; startsOn: string } // каждые N недель от реальной даты выплаты
  | { kind: 'one-off'; date: string }                     // разовый гонорар
  | { kind: 'irregular' };                                // «когда как» — в план не идёт, только факт

export type IncomeAmount =
  | { kind: 'absolute'; amountMinor: bigint }
  | { kind: 'percent'; percent: string; ofMinor: bigint }; // аванс 40% от оклада

export interface IncomeSource {
  readonly id: string;
  readonly label: string;                      // «Аванс», «Зарплата», «Подработка»
  readonly currency: string;                   // фриланс в USD — не обязательно базовая
  readonly schedule: IncomeSchedule;
  readonly amount: IncomeAmount;
  readonly stability: 'fixed' | 'variable';    // оклад vs плавающее
  readonly active: boolean;
  readonly startsOn?: string;                  // источник появился (новая работа)
  readonly endsOn?: string;                    // источник кончился (уволился) — прогноз это знает
}

export interface IncomeEvent {
  readonly sourceId: string;
  readonly label: string;
  readonly date: string;          // фактическая дата прихода (после правила выходных)
  readonly amountMinor: bigint;   // в валюте источника
  readonly currency: string;
}
```

`percent` — десятичная строка (как `envelopes.rule_value`), считается в BigInt без float. Деньги в jsonb хранятся строками-целыми и парсятся в bigint на границе — bigint в JSON не кладём.

### Функции

| Функция | Ответственность |
|---|---|
| `amountOfSource(source)` | `IncomeAmount` → bigint в валюте источника. `percent` → `floor(ofMinor × percent / 100)` в BigInt (планирование, не платёж). |
| `incomeEventsIn(sources, period, weekendRule)` | События внутри `[startsOn, endsOn)`. Учитывает `active`, `startsOn`/`endsOn` источника, правило выходных, кламп коротких месяцев. `irregular` → ничего. |
| `expectedIncomeForPeriod(events, toBase)` | `{ incomeMinor, unresolved }` в базовой валюте. `toBase: (Money) => Money \| null` — чистая инъекция, ядро не знает про БД и FX-кеш; `null` → приход попадает в `unresolved`, а не молча в ноль. |
| `rhythmMismatches(rhythm, sources, weekendRule)` | Список предупреждений вида «период начинается 10-го, ни один источник в этот день не платит». Информационно, не блокирует. |

### Правка `periods.ts`

`WeekendRule` и `shiftForWeekend(date, rule)` живут в `periods.ts`, а не в `income.ts`: даты и границы — его предметная область, и обратный импорт создал бы цикл (`periods` → `income` → `periods`). `income.ts` импортирует их оттуда.

`PeriodConfig` получает необязательное поле `weekendRule?: WeekendRule` (дефолт `'as-is'`). Сдвиг применяется **внутри генераторов дат, до сборки периодов** — иначе граница периода разъезжается с фактическим приходом. После сдвига массив дат сортируется и дедупится (сдвиг двух соседних дат может дать одну).

Дефолт `'as-is'` сохраняет текущее поведение и существующие тесты; сигнатура `generatePeriods(config, from, count)` не меняется.

## Инварианты

1. **Ритм обязателен и один; источник — минимум один активный.** Нет ритма или нет ни одного активного источника → онбординг не завершён, план не собирается (существующая ошибка `onboarding_incomplete`).
2. **Кламп коротких месяцев не создаёт лишних периодов.** Дни 30 и 31 в феврале схлопываются в одну дату: период один, приходов внутри — два (события не дедупятся, суммируются естественно, потому что доход периода — сумма списка).
3. **`irregular` в план не входит вообще.** Только факт (Спринт 3).
4. **`variable` планируется консервативно** — пользователь вводит нижнюю оценку («обычно от X»), план строится по ней. Завышенная цифра дня — самая дорогая ошибка продукта: человек тратит деньги, которых нет. После Спринта 3 медиана факта заменяет ручную оценку.
5. **Курс недоступен → приход в `unresolved`,** не ноль. Молчаливый ноль занижает доход и раздувает сжатие каскада.
6. **Правка источника не двигает границы периодов.** Границы зависят только от ритма → история планов не переезжает при добавлении подработки.
7. **Смена ритма — явное действие с предупреждением,** а не побочный эффект правки источника.
8. **Сумма процентов не валидируется жёстко.** В плоском списке нет группы, по которой суммировать: «аванс 40%» и «зарплата 60%» — два независимых источника, модель не знает, что это один оклад. Вместо блокировки — подсказка в форме («в сумме 90% от 200 000 — 10% нигде не учтены»).

## Схема данных

```sql
create table income_sources (
  id uuid primary key default gen_random_uuid(),
  workspace_id uuid not null references workspaces on delete cascade,
  label text not null,
  currency char(3) not null,
  schedule jsonb not null,                     -- IncomeSchedule (@multa/core)
  amount jsonb not null,                       -- IncomeAmount; суммы — строки-целые minor
  stability text not null default 'fixed' check (stability in ('fixed','variable')),
  active boolean not null default true,
  starts_on date,
  ends_on date,
  sort integer not null default 0,
  created_at timestamptz not null default now()
);
create index income_sources_ws_idx on income_sources (workspace_id, sort);
```

Изменения `workspaces`:
- `period_anchors jsonb` — **остаётся**, это ритм планирования (комментарий в схеме и доке переписать: «ритм планирования», не «якоря выплат»).
- `payday_weekend_rule text not null default 'before'` — **добавить**, `check in ('as-is','before','after')`. Дефолт `'before'`: и в РФ, и в Сербии выплату переносят на предшествующий рабочий день.
- `expected_income_minor bigint` — **удалить**. Доход периода живёт в `pay_periods.expected_income_minor` и считается по событиям.

`recurring_items`: из `check (kind in (...))` убрать `'income'`. Каноническая правда о доходах — `income_sources`; [#21](https://github.com/GarroV/multa/issues/21) строит только расходную часть. Две таблицы про доходы = гарантированный дрейф, поэтому развязка делается здесь, а не «потом».

Миграция — одна, `0001_add_income_sources.sql` (Drizzle: правка `schema.ts` → `drizzle-kit generate --name add_income_sources`), чистая, без бэкфила: pre-launch, значимых данных нет. Воркспейсы без источников считаются незавершённым онбордингом и проходят шаг дохода заново — включая прод-воркспейс основателя.

Почему таблица, а не jsonb-массив на воркспейсе: у набора источников появляется CRUD, история (`starts_on`/`ends_on`) и своя валюта на источник; правка элемента внутри jsonb-массива — гонки на чтение-модификацию-запись.

## API

| Метод | Назначение |
|---|---|
| `GET /v1/income-sources` | Список источников воркспейса (скоуп из токена, правило 7). |
| `POST /v1/income-sources` | Создать. |
| `PATCH /v1/income-sources/:id` | Правка (проверка принадлежности воркспейсу). |
| `DELETE /v1/income-sources/:id` | Удалить. |
| `POST /v1/onboarding/income` | Атомарно: ритм + правило выходных + набор источников одной транзакцией. Заменяет `POST /v1/onboarding/payday`, чтобы шаг не оставлял полусостояние. |
| `PATCH /v1/workspace` | Правка ритма и правила выходных из настроек. |

`GET /v1/plan/current` дополняется блоком `income`:

```jsonc
"income": {
  "expectedMinor": "11000000",
  "events": [ { "sourceId": "…", "label": "Аванс", "date": "2026-08-10", "amountMinor": "8000000", "currency": "RUB" } ],
  "unresolved": [ { "sourceId": "…", "label": "Фриланс", "currency": "USD", "reason": "rate_unavailable" } ]
}
```

Zod на границе: `discriminatedUnion` по `schedule.kind` и `amount.kind`; суммы через существующий `minor`; `days` — 1..31, непустой, дедуп; `weeks` ≥ 1; `percent` — десятичная строка в `(0, 100]`; `weekendRule` — enum. Даты — `YYYY-MM-DD`.

`assemble.ts`: `incomeMinor` больше не читается из воркспейса, а считается для конкретного периода через `incomeEventsIn` + `expectedIncomeForPeriod`. Курсы предзагружаются одним пакетом для валют активных источников (`Promise.all(getRate(...))`) и передаются в ядро замыканием — без FX и async внутри `@multa/core`. Следствие: план периода 10–25 и 25–10 различаются, конверты-проценты считаются от реального дохода периода.

Гейт онбординга (`/v1/me`): вместо «есть `periodAnchors`» — «есть ритм **и** хотя бы один активный источник». Поле `expectedIncomeMinor` из DTO воркспейса уходит.

## Интерфейс шага «Когда приходят деньги»

Снимает жалобу «10-е/25-е и каждые две недели — это одно и то же»: вместо выбора ярлыка показываем последствия.

**Блок 1 — ритм.** Три варианта, у каждого превью реальных дат, которые сгенерит `generatePeriods`:

```
Два раза в месяц   ·  дни [10] [25]   →  10 авг · 25 авг · 10 сен
Раз в месяц        ·  день [25]       →  25 авг · 25 сен · 25 окт
Цикл в N недель    ·  [2] нед. от [8 авг]  →  8 авг · 22 авг · 5 сен
```

Дни и даты — редактируемые поля, не зашитые константы; для цикла недель дата ближайшей или последней выплаты обязательна (сегодняшняя дата в качестве якоря — источник дефекта #27). Видно, что во втором случае даты плывут по календарю (26 выплат в год против 24) — разница перестаёт быть спором о словах. Правило выходных — селект из трёх значений, превью немедленно пересчитывается.

**Блок 2 — сколько приходит.** Список выплат, предзаполненный днями из блока 1 (дни набираются один раз): `метка · день · сумма` + переключатель «процентом от оклада» (тогда поле оклада и процент), + «добавить выплату», ✕ на удаление. Сид: «Аванс» 10-е, «Зарплата» 25-е, суммы пустые. Подсказка суммы процентов — информационная. Если день выплаты не совпадает ни с одной границей периода — мягкое предупреждение со ссылкой «поправить ритм».

**Блок 3 — «Есть ещё источники дохода?»** Пропускаемо. Заготовки: подработка (цикл в 1 неделю), разовый гонорар (`one-off`), «когда как» (`irregular`). Валюта на источник. Большинству хватит первых двух блоков, и третий не должен утяжелять первый вход.

Превью дат считает `@multa/core` **на клиенте** (пакет уже импортируется в web) — совпадение превью с сервером получается конструктивно, а не проверкой.

Настройки (`Settings.tsx`) используют тот же редактор: сейчас там второе место правды с теми же пресетами. `apps/web/src/lib/paydayPresets.ts` удаляется целиком, ключи `onboarding.payday.preset.*` и `onboarding.payday.expectedAmount` — из ru и en. Новые ключи — `income.*`. Только семантические CSS-переменные и существующие `.chip/.field/.mono/.btn`.

## Тесты

**core** (`income.test.ts`, `periods.test.ts`):
- события при смешанных расписаниях (10/25 + недельная подработка в том же периоде);
- полуоткрытость границ: приход в день `endsOn` относится к следующему периоду;
- кламп февраля: дни 30 и 31 → один период, два прихода;
- `percent` → суммы в BigInt, без float, floor;
- сдвиг по выходным меняет **границу** периода (правило на воркспейсе) и дату события согласованно;
- `irregular` не даёт событий; `one-off` вне периода не даёт события;
- `startsOn`/`endsOn` источника обрезают события; `active: false` исключает;
- недоступный курс → `unresolved`, `incomeMinor` не занижен молча;
- инвариант: `expectedIncomeForPeriod` = сумма `incomeEventsIn` (приведённая к базовой).

**api**:
- схемы: невалидный `day`, `percent` вне диапазона, сумма не-целая, неизвестный `kind` → 400;
- CRUD: источник чужого воркспейса не читается и не правится (404);
- `/v1/plan/current` для периода 10–25 и 25–10 даёт разные `expectedMinor`;
- `POST /v1/onboarding/income` атомарен: падение на втором источнике не оставляет первый;
- воркспейс без источников → `onboarding_incomplete` (409).

**web (e2e Playwright)**:
- проход шага: ритм → суммы → второй источник → план собран;
- превью дат в UI совпадает с датами из `generatePeriods`;
- редактируемый день для «раз в месяц» и обязательная дата для цикла недель (регресс #27).

## Сознательно не делаем

- Произвольные RRULE в интерфейсе (модель их не описывает; библиотеку `rrule` не тянем — 687 КБ и вторая арифметика дат поверх нашей на UTC-строках).
- `weekly` отдельным видом расписания — это `every-weeks` с `weeks: 1`.
- «Последняя пятница месяца» (`monthly-nth-weekday`) — до первого реального запроса.
- Правило выходных на источник (пока одно на воркспейс: это конвенция платёжного календаря страны, а не свойство работы; при необходимости добавляется переопределением без миграции данных).
- Налоги, gross/net, разные суммы по неделям внутри недельного расписания.
- Медиана факта для `variable` — ждёт Спринта 3 (#4).
- Общий «оклад» для группы процентных источников: в плоском списке оклад дублируется в каждом процентном источнике, форма подставляет уже введённое значение. Если на dogfooding это заболит — добавляется необязательное поле группы, старые данные не ломаются.

## Ресерч

- **Firefly III** (`recurrences`): `repeat_type` = `daily|weekly|ndom|monthly|yearly` + `moment`, отдельная политика выходных из четырёх значений (как есть / пропустить / предшествующая пятница / следующий понедельник). Подтверждает и таксономию, и отдельное правило выходных; там же известный класс баг-репортов «31-е в феврале» — наш кламп коротких месяцев.
- **Actual Budget** (`schedules`): одно расписание допускает несколько дат — подтверждает `monthly-days` со списком дней.
- **`rrule@2.8.1`**: 687 КБ unpacked, работает на `Date` и таймзонах. У нас в `periods.ts` своя арифметика на UTC-строках под тестами; библиотека дала бы второй способ считать даты и съела бюджет бандла. Берём таксономию и правило выходных, библиотеку — нет.
